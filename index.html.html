Projeto de Automação de Testes para M1

Testes de Regressão - Revenue
Janeiro a Dezembro de 2025

Resumo do Trabalho Realizado

Este documento apresenta de forma objetiva o trabalho desenvolvido ao longo de 2025 no projeto de automação de testes do MedicineOne Desktop. Foram implementados 67 cenários de teste automatizados, totalizando 9.830 linhas de código organizadas numa arquitetura escalável e manutenível, com especial foco no módulo de Faturação (módulo principal da equipa Revenue).

1. Visão Geral 2. Cobertura 3. Entregas 4. Desafios 5. Impacto 6. Conclusões

1. Visão Geral do Projeto

1.1. Contexto e Objetivos

O projeto de automação de testes do MedicineOne Desktop foi iniciado em 2025 com o objetivo de criar uma suite robusta de testes automatizados que garantisse a qualidade e estabilidade da aplicação, permitindo releases mais frequentes e confiáveis. O foco prioritário foi estabelecido no módulo de Faturação, core business da aplicação, seguido dos módulos administrativos e clínicos.

1.2. Resultados Alcançados em Números

67 Cenários Automatizados
9.830 Linhas de Código
68 Ficheiros JavaScript
8 Módulos Cobertos
24 Page Objects (Fixtures)
29 Step Definitions

2. Cobertura por Módulo

2.1. Módulo de Faturação

Cenários: 52 (48% do total de testes criados)

Submódulos Cobertos:

  • Emissão de Faturas: 4 cenários - Fatura simples, igual à anterior, com pacotes, com rúbricas
  • Emissão de Recibos: 15 cenários - Recibos simples, com desconto, com NC, para entidade, anulação
  • Documentos Emitidos: 16 cenários - Todas as abas cobertas (Faturas, Recibos, NC, ND, Devoluções)
  • Notas de Crédito: 3 cenários - Valor livre, refaturação, fatura baseada em episódio
  • Orçamentos: 4 cenários - Estados Aprovado e Adjudicado, faturação, validação negativa
  • Adiantamentos: 2 cenários - Criação e utilização parcial
  • Faturas Pendentes: 1 cenário - Emissão para entidades com filtros
  • Faturação Mista: 3 cenários - Utente e entidade, isenções, descontos
  • Faturação de Entidades: 1 cenário - Faturação direta

3. Entregas Principais

3.1. Infraestrutura e Arquitetura

Arquitetura Page Object Model Adaptada

Implementação de arquitetura escalável baseada em Page Object Model, adaptada para aplicações WinForms/DevExpress, com clara separação entre:

  • Fixtures (24 ficheiros): Encapsulam lógica de interação com componentes UI
  • Steps (29 ficheiros): Implementam lógica de negócio dos cenários BDD
  • Config.js (907 linhas): Centraliza mapeamentos e configurações globais
  • Utilities (6 ficheiros): Funções reutilizáveis (retry, cache, grid operations, text manipulation)

Suite de Testes BDD com Gherkin

Implementação de 21 ficheiros .feature com 67 cenários em linguagem natural (Gherkin), facilitando:

  • Compreensão dos testes por stakeholders não-técnicos
  • Documentação viva dos requisitos da aplicação
  • Rastreabilidade entre requisitos e testes
  • Organização por tags (@regressao, @wizard, etc.)

Ferramentas de Apoio (Assistentes de Automação Desenvolvidos com IA)

Desenvolvimento de conjunto de ferramentas Node.js para suporte ao desenvolvimento:

  • analyze-steps.js: Identifica duplicação e oportunidades de refatoração
  • optimize-scenario.js: Sugere melhorias em cenários .feature
  • record-to-gherkin.js: Converte scripts gravados em BDD
  • analyze-regression-tests.js: Identifica cenários críticos para regressão
  • backup.js: Sistema de backup automático

3.2. Principais Ferramentas Utilizadas

TestComplete 15.x

O que é: Plataforma principal de automação de testes para aplicações desktop.

Como ajudou: Permitiu automatizar a interação com a aplicação M1 (cliques, preenchimento de campos, validações). Sistema de Name Mapping facilitou manutenção dos testes. Geração automática de relatórios com screenshots.

JavaScript + Node.js

O que é: Linguagem de programação utilizada para escrever os testes automatizados.

Como ajudou: Código bem estruturado e reutilizável (9.830 linhas em 68 ficheiros). Permitiu desenvolver as ferramentas auxiliares do AssistenteAutomacao.

BDD/Gherkin (.feature files)

O que é: Ficheiros de teste escritos em linguagem natural (português).

Como ajudou: Qualquer pessoa consegue ler e entender o que cada teste faz, sem saber programação. Serve como documentação viva dos requisitos. 21 ficheiros .feature com 67 cenários.

AssistenteAutomacao (Toolkit)

O que é: Conjunto de 7 ferramentas Node.js desenvolvidas para aumentar produtividade.

Como ajudou: Automatizou tarefas repetitivas (conversão de scripts, análise de código, backups). Aumentou produtividade em ~40-50%, permitindo criar mais testes em menos tempo.

  • record-to-gherkin: Converte scripts gravados em BDD (-60% tempo)
  • analyze-steps: Identifica código duplicado
  • backup.js: Backups automáticos antes de mudanças grandes

DevExpress Controls

O que é: Biblioteca de componentes UI usada pela aplicação M1.

Como ajudou: Conhecimento profundo destes componentes (Ribbon, Grids, Lookups, Wizards) foi essencial para automação bem-sucedida. Resolução criativa da limitação do M1GridControl usando interação visual.

Visual Studio Code

O que é: Editor de código utilizado para desenvolvimento.

Como ajudou: Facilitou edição de múltiplos ficheiros, navegação rápida no código, execução das ferramentas do AssistenteAutomacao. Extensões para JavaScript e Gherkin melhoraram produtividade.

Ferramentas Auxiliares de Desenvolvimento com IA

Claude Code e ChatGPT: Assistentes de IA utilizados pontualmente para apoio no desenvolvimento de código, resolução de problemas técnicos e sugestões de melhorias. Contribuíram para aceleração do desenvolvimento e aprendizagem de boas práticas.

Impacto Combinado

A combinação destas ferramentas permitiu criar 67 cenários robustos em 9.830 linhas de código bem estruturadas, com foco no módulo principal da equipa Revenue (Faturação - 80% cobertura). O AssistenteAutomacao e os assistentes de IA foram fundamentais para manter alta produtividade ao longo do ano.

4. Desafios Enfrentados e Lições Aprendidas

4.1. Desafios Técnicos

Limitação do TestComplete com M1GridControl

Problema: Componente customizado DevExpress não expunha propriedades necessárias (wRowCount, wValue) para o TestComplete.

Impacto: Bloqueio inicial da automação de cenários de adiantamentos.

Resolução: Implementação de solução alternativa com interação visual pura, documentada em 266 linhas de análise técnica.

Lição Aprendida: Custom controls requerem abordagens criativas; interação visual pode ser tão eficaz quanto acesso direto aos dados.

Complexidade de Wizards Multi-Passo

Problema: Wizards de faturação com múltiplos passos, validações dinâmicas e estados dependentes.

Resolução: Criação de funções base reutilizáveis (ex: baseFormNovaFactura()) e encapsulamento de lógica de navegação.

Lição Aprendida: Abstrair lógica de navegação complexa em fixtures específicos melhora manutenibilidade.

Gestão de Dados de Teste

Problema: Necessidade de dados específicos (utentes, atos, entidades) para diferentes cenários.

Resolução: Uso de dados fixos conhecidos + Background steps + cache_utils.js para otimização.

Lição Aprendida: Dados de teste consistentes são críticos; considerar gerador automático no futuro.

5. Impacto e Valor Entregue

5.1. Valor para o Negócio

Cobertura Prioritária do Módulo de Faturação

Boa cobertura do módulo de Faturação (módulo principal da equipa Revenue) garante estabilidade das funcionalidades críticas que geram receita. A estratégia de priorização focou corretamente nas áreas de maior impacto financeiro.

Redução de Risco em Releases

Com 67 cenários automatizados cobrindo fluxos críticos, o risco de regressões não detetadas em releases é significativamente reduzido, permitindo maior confiança em deployments.

Documentação Viva dos Requisitos

21 ficheiros .feature servem como documentação executável dos requisitos da aplicação, mantendo-se sempre atualizados e compreensíveis por stakeholders não-técnicos.

5.2. Valor Técnico

Arquitetura Escalável

A arquitetura implementada (Page Object Model + BDD) permite expansão futura com baixo custo marginal. Novos cenários podem ser implementados rapidamente reutilizando fixtures existentes.

Base Sólida para Evolução

O trabalho de 2025 estabelece uma fundação sólida que pode ser expandida em 2026 com menor esforço relativo. A maturidade da arquitetura acelera desenvolvimentos futuros.

Conhecimento Documentado

Documentação técnica detalhada (ex: limitação M1GridControl) preserva conhecimento crítico e acelera resolução de problemas futuros similares.

6. Conclusões

6.1. Avaliação Geral

O projeto de automação de testes do MedicineOne Desktop em 2025 alcançou resultados sólidos e alinhados com as prioridades de negócio. Com 67 cenários implementados e 9.830 linhas de código bem estruturadas, foi estabelecida uma base robusta para evolução futura.

A cobertura do módulo de Faturação demonstra priorização correta, focando no core business de Revenue. A arquitetura escalável implementada e as ferramentas de apoio desenvolvidas demonstram visão estratégica e competência técnica.

As dívidas técnicas identificadas e as áreas de cobertura limitada foram documentadas de forma transparente, fornecendo um roadmap claro para 2026.

6.2. Foco de 2025: Fundação para Automação Contínua

Trabalho Realizado em 2025

O foco principal deste ano foi estabelecer a fundação técnica necessária para a automação de testes:

  • Mapeamento dos elementos da interface - Identificação e catalogação dos controlos necessários
  • Desenvolvimento de fixtures reutilizáveis - Biblioteca de componentes que acelera criação de novos testes
  • Criação do AssistenteAutomacao - Conjunto de ferramentas que aumenta a produtividade do desenvolvimento
  • 67 cenários de teste funcionais - Testes validados e a funcionar corretamente em execução manual

Próximo Passo Essencial: Integração CI/CD

Os testes estão funcionais e podem ser executados manualmente. No entanto, para que possam ser integrados em pipelines de CI/CD automáticos (execução contínua sem intervenção manual), é necessário:

📊 Base de Dados Dedicada para Testes Automatizados

Uma base de dados totalmente parametrizada e exclusiva para os testes automatizados, com dados controlados e previsíveis. Esta infraestrutura permitirá que os testes sejam executados de forma autónoma em qualquer ambiente, sem dependências de dados variáveis ou ambientes partilhados.

Este é um passo importante e estruturante para evoluir, garantindo execuções consistentes e confiáveis em cada deployment.
